Inter-Process CommunicationHow isolated processes share data, and how they take turns without breaking it

Every process has its own private memory, so talking to another process means going through the kernel or sharing a region of memory. This page walks through both models, then the four classic problems that show what goes wrong.

Two ways to communicate

An OS can provide both. In shared memory, the processes move the data themselves. In message passing, the kernel moves it for them. Step through each to see where the copies and system calls happen.

Dining Philosophers: deadlock and starvation

Five philosophers, five forks, and each needs both neighbouring forks to eat. Every fork is a semaphore. Run it, then press everyone hungry at once in naive mode.

thinkinghungry, no forksholding 1 forkeatingtold to wait
Strategy
Run
What's happening
Meals eaten
  • Deadlock needs all four Coffman conditions: mutual exclusion, hold and wait, no preemption, circular wait. Break any one of them and deadlock can't happen.
  • Ordered forks breaks circular wait: everyone picks up the lower-numbered fork first, so P4 reaches for f0 before f4.
  • Waiter uses a counting semaphore room = 4. With at most 4 philosophers competing for 5 forks, at least one always gets two.
Semaphore pseudocode
semaphore fork[5] = {1,1,1,1,1};

philosopher(i):
  while (true) {
    think();
    wait(fork[i]);              // left
    wait(fork[(i+1) % 5]);      // right  ← all five can block here: deadlock
    eat();
    signal(fork[i]);  signal(fork[(i+1) % 5]);
  }
// fix A: wait on min(i,(i+1)%5) first      fix B: wait(room) before the forks, signal(room) after

    Readers–Writers: share reads, guard writes

    Any number of readers can read at once, because reading changes nothing. A writer needs the data to itself. The hard part is fairness. Add a writer, turn on the reader flood, and watch the writer starve.

    What's happening
    • The first reader in locks rw_mutex for every reader. The last reader out releases it. Writers simply wait on rw_mutex.
    • With reader preference, a steady stream of readers keeps read_count above 0 forever, so writers starve.
    • Fair or writer-priority rules (a FIFO queue or an extra turn semaphore) make new readers queue behind a waiting writer.

    semaphore rw_mutex = 1, mutex = 1;   int read_count = 0;

      Race condition

      The output depends on the timing of the interleaving. Fix it with mutual exclusion.

      Deadlock

      A cycle of processes, each holding a resource the next one needs. Requires all four Coffman conditions.

      Starvation

      A process is ready but always loses to others. Fix it with fairness, aging or priority rules.

      Data inconsistency

      Shared data is read while half updated. Fix it with critical sections.

      Overhead and security

      System calls and copies cost time, and a shared region can leak data between processes.

      Scalability

      The more processes share one lock, the more of them wait. Fine-grained locking spreads that out.

      System calls follow POSIX and Linux conventions. Buffer sizes and timings in the simulations are simplified for clarity.
